# Internal Certificate Management

The `proxy` CT runs Nginx Proxy Manager (NPM). Internal TLS certificates are issued
by the `internal_ca` Ansible role and must be signed by the current root CA:

| Item | Value |
|---|---|
| Root CA | `Omni Homelab Root CA` |
| Root CA SHA-256 | `4F:A6:82:30:2A:5E:E5:50:C0:E9:97:5A:07:A3:3E:F4:4E:36:97:D1:36:F8:69:E0:36:0B:28:81:5F:2D:7F:B1` |
| Key pair | `/opt/internal-ca/private/ca.key` and `/opt/internal-ca/certs/ca.crt` |
| Root key backup | Stored offline by the operator; never commit it to Git |

The root CA must not be regenerated as part of routine certificate work. The role
fails if only one half of the root key pair exists.

## Certificate inventory

The role supports multiple certificates under the same root CA. Current production
certificates:

| NPM name | SAN | Used by |
|---|---|---|
| `Omni Homelab Wildcard` | `*.omni.corp`, `omni.corp` | Single-label `*.omni.corp` proxy hosts |
| `Omni Homelab Hearthlane Wildcard` | `*.hearthlane.omni.corp`, `hearthlane.omni.corp` | `frigate`, `relay` and `relay-uat` under `hearthlane.omni.corp` |

NPM assigned IDs 3 and 4 during the migration. These IDs are runtime values. The
role identifies certificates by exact `nice_name` and uses the ID returned by the
NPM API; do not hardcode IDs in automation.

The legacy `Omni Corp` certificate (currently ID 2) is retained for rollback. It is
not associated with any proxy host after the migration.

Certificate files and keys are stored on the `proxy` CT:

```text
/opt/internal-ca/certs/<common-name>.crt
/opt/internal-ca/certs/<common-name>.fullchain.crt
/opt/internal-ca/private/<common-name>.key
```

## Lifecycle

The role supports automatic renewal, explicit renewal and key rotation:

- Automatic renewal when the certificate enters
  `internal_ca_cert_renewal_threshold_days` (default 30 days).
- Automatic reissue when required extensions, SAN coverage, CA signature or key
  correspondence are missing or invalid.
- `internal_ca_force_certificate_renewal=true` reissues with the existing key.
- `internal_ca_rotate_certificate_keys=true` generates a new key and reissues.
- Explicit operations are one-off extra variables; do not store them permanently in
  inventory.

Examples:

```bash
ansible-playbook playbooks/certificates.yml --limit proxy \
  -e internal_ca_force_certificate_renewal=true

ansible-playbook playbooks/certificates.yml --limit proxy \
  -e internal_ca_rotate_certificate_keys=true
```

`playbooks/certificates.yml` runs only the certificate lifecycle role. Use
`playbooks/proxy.yml` when the full NPM proxy host configuration should also be
reconciled.

Renewal and rotation use staged files, validate the staged certificate and key, and
install them only after validation succeeds. The legacy key and certificate are
backed up under `/opt/internal-ca/backups/<name>/<timestamp>/`.

## X.509 requirements

New root CAs generated by the role contain:

- `basicConstraints=critical,CA:TRUE`
- `keyUsage=critical,keyCertSign,cRLSign`
- Subject and authority key identifiers

Server certificates contain:

- `basicConstraints=critical,CA:FALSE`
- `keyUsage=critical,digitalSignature,keyEncipherment`
- `extendedKeyUsage=serverAuth`
- Subject and authority key identifiers
- SAN entries from `internal_ca_domains[].san`

The existing root CA predates the key-usage requirement and does not contain a
`keyUsage` extension. It is intentionally not regenerated. Creating a new root CA
requires a separate migration and redistribution to every client.

## NPM integration

`inventories/lab/host_vars/proxy/vars.yml` defines the certificates and their proxy
hosts:

```yaml
internal_ca_domains:
  - name: "*.omni.corp"
    common_name: "*.omni.corp"
    npm_nice_name: "Omni Homelab Wildcard"
    san:
      - "*.omni.corp"
      - "omni.corp"
    npm_proxy_hosts:
      - vault.omni.corp
```

For every configured certificate the role:

1. resolves the NPM certificate by exact `nice_name`;
2. creates the certificate record when absent;
3. validates that every managed proxy host is covered by the certificate SAN;
4. validates that every managed proxy host exists exactly once in NPM;
5. uploads the leaf certificate, private key and CA chain;
6. compares the stored certificate fingerprint, public key and chain length to the
   IaC files and skips the upload when they already match;
7. associates only the configured proxy hosts using the NPM certificate ID;
8. sends only `certificate_id` on proxy host updates, preserving all other settings;
9. reloads NPM and verifies the served endpoints.

Do not add a host with extra labels to the `*.omni.corp` list. Use a certificate
whose SAN covers that host.

## Verification

Run the read-only verification playbook:

```bash
ansible-playbook playbooks/verify-certificates.yml --limit proxy
```

For every managed proxy host it verifies:

- the TLS chain against `Omni Homelab Root CA`;
- hostname/SAN compatibility;
- the SHA-256 fingerprint served through SNI;
- certificate validity;
- `digitalSignature`, `keyEncipherment`, `serverAuth` and `basicConstraints`;
- certificate and private key correspondence;
- complete fullchain;
- HTTPS connectivity.

The playbook fails if NPM serves a certificate different from the IaC certificate.
Application HTTP errors are separate from TLS validation failures.

A successful deployment is not a dry run for a later change: `ansible.builtin.uri`
does not support check mode reliably. Use lint and syntax checks before applying.

## Migration procedure

1. Verify the root CA key, root fingerprint and NPM health.
2. Identify all proxy hosts and their current certificate IDs.
3. Create a restorable Proxmox backup of CT 101:

   ```bash
   vzdump 101 --storage local --mode suspend --compress zstd \
     --notes-template "pre-certificate-migration"
   ```

4. Validate the repository:

   ```bash
   yamllint .
   ansible-lint .
   ansible-playbook playbooks/proxy.yml --syntax-check
   ansible-playbook playbooks/verify-certificates.yml --syntax-check
   ```

5. Apply the certificate lifecycle role:

   ```bash
   ansible-playbook playbooks/certificates.yml --limit proxy
   ```

6. Run the independent verification playbook.
7. Validate critical clients, including Android and Vaultwarden.
8. Run the deployment a second time and confirm it reports no changes.

For Vaultwarden, HTTP-to-HTTPS redirection is enabled. HSTS is not enabled.
Vaultwarden data, credentials and volumes must not be changed during certificate
work.

## Rollback

Preferred rollback is restoring the pre-migration CT backup:

```bash
pct restore 101 /var/lib/vz/dump/vzdump-lxc-101-<timestamp>.tar.zst   --storage local-lvm --force
```

Confirm free space on `local-lvm` before restoring. `--force` replaces the existing
CT; if the thin pool cannot hold the extraction temporarily, free unused volumes or
restore to a temporary CT and copy the required data.

Logical rollback without restoring the CT:

1. Resolve the legacy certificate by exact `nice_name="Omni Corp"` through the NPM
   API.
2. Update each migrated proxy host with only its legacy `certificate_id`.
3. Reload NPM.
4. If rolling back Vaultwarden redirect behavior, set `ssl_forced` back to `false`
   through the NPM API.

The legacy certificate record and its files under `custom_ssl/npm-2` are preserved
during migration. Do not delete them until the migration is accepted and the
rollback window has closed.

File-level fallbacks:

- `/opt/internal-ca/backups/<name>/<timestamp>/` for renewed/rotated IaC files.
- `/data/custom_ssl/backups/npm-<certificate-id>/<timestamp>/` for NPM certificate
  files that existed before an upload.

Android clients trust the root CA, not the leaf certificate. Rolling back to the
legacy certificate also requires the legacy root CA to be trusted by the client.

## Notes and limitations

- The current root CA has `CA:TRUE` but no `keyUsage`; this is a pre-existing
  limitation.
- NPM may display `domain_names` as `["BR,"]` for custom certificates because its
  CN parser reads the first RDN of a multi-field subject. Automation does not rely
  on this field.
- Certificate and NPM backups are not pruned automatically.
- Do not enable HSTS as part of a routine certificate change.
